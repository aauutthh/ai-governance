# pseudocode-system.md

伪代码系统规范

## 一、设计目标

本伪代码系统用于 AI 在**设计阶段**产出文档时描述逻辑，不是最终代码。
在设计阶段，用统一伪代码表达流程、状态、约束、异常和数据流，避免过早进入具体语言实现。
设计要求: 易读性、无歧义性、表达能力、AI 友好、符号哲学一致

**使用时机**：除最终编码阶段外，任何阶段的逻辑描述均使用本系统表示。

**设计原则**：
- 去除语言实现细节（生命周期、模块路径、宏等），保留语义
- 重要/关键实现，其生命周期、所有权转移的说明（需人类可读可理解）写到注释
- 符号体系具备一致性哲学，降低记忆成本
- 兼顾人类可读性与 AI 可解析性

## 二、符号哲学

同一符号可同时体现多个特征（复合符号），通过前缀/后缀规律组合语义：

| 符号特征 | 关联语义 | 代表符号 |
|----------|----------|----------|
| 以 `:` 结尾 | 解释、定义、声明 | `:`、`>>:`、`<<:`、`///:` |
| 以 `::` 分隔 | 命名空间 | `@DB::insert`、`@Cache::set` |
| 以 `>` 结尾 | 流程、转换、处理，或表明方向 | `->`、`\|\|->`、`-->`、`*->` |
| 以 `<` 开头 | 表明方向 | `<-->`、`<-*` |
| 以 `==` 结尾 | 等待相关 | `\|\|==` |
| 以 `&` 开头 | 引用相关 | `&fn xxx` 表示函数引用（闭包/回调） |
| 以 `!` 开头 | 错误、警醒 | `!`、`!!`、`!Type{->}` |
| 以 `?` 开头 | 分支判断 | `?=`、`?key=` |
| 以 `@` 开头 | 副作用（IO/事件/外部调用） | `@DB::save`；一般在流程中使用，表示某个动作有副作用 |
| 以 `*` 开头或结尾 | 锚点及方向，触发 | `*->`、`<-*` |
| 以 `\|\|` 开头 | 并发相关 | `\|\|->`、`\|\|==` |
| 被 `()` 包围 | 组合 | `!(Err1\|Err2)` |
| 被 `\|` 分隔 | 组合中的并操作 | `!(Err1\|Err2)` |
| 被 `{}` 包围 | 结构性，子流程块 | `!Type{->act}` |
| 被 `""` 包围 | 字面量，消除特殊符号引起的歧义 | `"publish@topics"` |
| 以 `\` 开头（`""` 内） | 转义；仅需转义 `\` 和 `"` | `"say \"hello\""` |
| `...` | 省略 | 聚焦核心时略去无关细节 |

**无关键字设计**：如 return、break 等全部按单词原语义理解。

**类型声明**：`:` 后面的类型声明采用 Rust 语义，但省略生命周期。其他解释内容按自然语义。

**命名空间**：`::` 分隔不影响逻辑含义。`@数据库::insert` 与 `@数据库插入` 等价，前者更利于结构化表达和 pattern 搜索。

**复合符号解读**：

| 符号 | 拆解 | 语义 |
|------|------|------|
| `>>:` | `>>` 数据流入 + `:` 定义 | 输入参数定义 |
| `<<:` | `<<` 数据流出 + `:` 定义 | 输出类型定义 |
| `*->` | `*` 触发锚点 + `->` 流转 | 触发并流转 |
| `<-*` | `<-` 方向 + `*` 触发锚点 | 逆向触发（`*->` 的对称形式） |
| `///:` | `///` 文档注释惯例 + `:` 定义 | 块注释起始 |

## 三、符号速查表

| 符号 | 适用场景 | 含义 |
|------|----------|------|
| `:` | 所有场景 | 定义分隔符；左侧为名，右侧为定义；定义换行时内容需缩进 |
| `>>:` | 函数定义 | 输入参数块起始；参数逐行缩进列出 |
| `<<:` | 函数定义 | 输出类型块起始；类型缩进列出 |
| `//` | 所有场景 | 单行注释（可行尾内联） |
| `///:` | 所有场景 | 块注释起始；注释内容缩进至下一行 |
| `->` | 函数实现 | 执行下一个动作；子步骤缩进两个空格 |
| `?=<value>` | 函数实现 | 分支条件；缩进于父步骤，对父步骤结果（单值）判断 |
| `?=` | 函数实现 | 无 value 时表示默认/else 分支 |
| `?<key>=<value>` | 函数实现 | 多返回值分支；对父步骤结果中指定 key 判断 |
| `?<key>=` | 函数实现 | 多返回值的默认分支 |
| `\|\|->` | 函数实现 | 并行分支起始（并行执行轨道） |
| `\|\|==` | 函数实现 | 并行合并点；合并方式由后面文字描述 |
| `::` | 函数实现 | 命名空间分隔符 |
| `@<操作>` | 函数实现 | 副作用标注；一般配合 `->` 使用 |
| `&fn <名>` | 函数实现 | 函数引用（闭包/回调），逻辑在函数外独立编写 |
| `!` | 函数实现 | 可恢复错误；附于步骤末尾；无处理则逐层向上抛出 |
| `!!` | 函数实现 | 不可恢复错误（panic，不可被上层捕获） |
| `!Type{->act}` | 函数实现 | 错误发生时执行 `act` 处理动作 |
| `{}` | 函数实现 | 多步骤子流程块 |
| `loop` | 函数实现 | 循环/迭代块起始 |
| `...` | 所有场景 | 省略无关细节 |
| `-->` | 状态机 | 状态单向可达；左侧源状态，右侧目标状态 |
| `<-->` | 状态机 | 状态双向可达 |
| `*->` | 状态机 | 状态转换的触发条件 |
| `<-*` | 状态机 | 状态逆转换的触发条件（仅用于 `<-->` 下） |

## 四、契约块

契约块用于描述**模块级别**的设计信息，位于模块或章节开头。

**格式**：

```
[模块] <模块名>
[功能及目的] <描述本模块的职责与目标>
[依赖] <所依赖的模块、服务或组件>
[边界] <负责什么；不负责什么>
```

**规则**：
- 每个 `[字段]` 独占一行
- `[边界]` 推荐格式：`负责：A、B` / `不负责：C`

**示例**：

```
[模块] OrderService
[功能及目的] 处理订单创建和状态流转的核心业务逻辑
[依赖] UserRepo、OrderRepo、StockService、EventBus
[边界]
    负责：业务校验、订单持久化、事件发布
    不负责：支付处理（PaymentService）、库存扣减（WarehouseService）
```

## 五、函数伪代码

### 5.1 函数签名

```
fn <函数名>:
    impl: <接口>
    >>:
        <参数名>: <类型>
        <参数名>: <类型>
    <<:
        <返回类型>
```

**规则**：
- `impl:` 表示该函数实现某个接口外观，可选
- 省略生命周期标注（`'a`、`'static` 等）
- 省略完整模块路径前缀（`crate::user::UserId` 写为 `UserId`）
- `>>:` 与 `<<:` 块内内容均缩进一级
- 无输入参数时 `>>:` 块可省略；不关心返回值时 `<<:` 块可省略
- 泛型保留（如 `Vec<Item>`），但省略约束（`T: Clone + Send`）

### 5.2 流程步骤

`->` 表示执行一个动作，自上而下按书写顺序依次执行：

```
-> <步骤A>
-> <步骤B>
    -> <子步骤B-1>      // 缩进两个空格
    -> <子步骤B-2>
-> <步骤C>
```

**规则**：
- `->` 仅表示「执行此动作」，不隐含成功或失败语义
- 子步骤的缩进层级体现调用层级，与错误处理层级无关
- 步骤一般优先是功能性的流程描述，如果可以用代码简洁表示也可以

### 5.3 函数分片约定

使用 `// <分片>: <描述>` 将函数体分为多个逻辑区域：

| 分片标记 | 含义 |
|----------|------|
| `// 前置: <描述>` | 数据获取、前提检查、必要资源加载 |
| `// 处理: <描述>` | 核心业务逻辑 |
| `// 后置: <描述>` | 持久化、事件发布、缓存更新等 |

**规则**：
- 逻辑超过 10 行建议分片
- 分片内容可以是各种高度概括性单词、tag、领域等，目的是人类快速掌握整块逻辑
- 结构体超过 10 行也建议分片

### 5.4 错误标注与处理

#### 5.4.1 基本错误标注

```
-> <步骤>  !<错误类型>
-> <步骤>  !<错误类型A>  !<错误类型B>    // 多个独立错误
-> <步骤>  !(<错误类型A>|<错误类型B>)    // 组合表示
```

无处理说明时，该错误向上层（逐层）抛出。

#### 5.4.2 带处理动作的错误

单行形式：
```
-> <步骤>  !<错误类型>{-><处理动作>}
```

多行形式：
```
-> <步骤>  !<错误类型>{
    -><处理动作>
    -><处理动作>
}
```

组合错误处理：
```
-> <步骤>  !(<错误类型A>|<错误类型B>){
    -><处理动作>
}
```

#### 5.4.3 不可恢复错误

```
-> <步骤>  !!<错误类型>
```

触发 panic，不可被上层捕获。

### 5.5 并行执行

```
-> <父步骤描述>
    ||-> <并行分支A>
    ||-> <并行分支B>
    ||-> <并行分支C>
    ||== 全部成功  !<错误类型A>  !<错误类型B>
```

**规则**：
- `||->` 分支缩进于父步骤下
- 所有 `||->` 分支并行执行，无顺序依赖
- `||==` 等待所有分支完成后，主流程继续；合并方式由 `||==` 后的文字描述
- 任一分支可能独立产生的错误，可在各分支标注或在合并点统一标注

### 5.6 分支判断

```
-> <产生判断结果的父步骤>
    ?=<条件A>{ -> <处理动作>}                    // 无 return：执行完继续后续步骤
    ?=<条件B>{ -> return Err(<错误类型>)}        // 有 return：立即终止函数
    ?={ -> <默认处理>}                           // else/默认分支
```

多返回值分支：
```
-> <产生多值结果的父步骤>
    ?<key>=<条件A>{ -> <处理动作>}
    ?<key>={ -> <默认处理>}
```

**规则**：
- `?=value` 必须缩进于其父步骤下
- `?=value` 后紧跟 `{->}` 描述该条件下的动作
- 含 `return`：立即终止函数，不执行后续任何步骤
- 不含 `return`：执行完该分支后，继续执行父步骤之后的下一步骤
- `?=` 无 value：表示默认/else 语义
- `?<key>=value`：对父步骤多返回值中的指定 key 进行判断

### 5.7 副作用

副作用使用 `@` 标注，配合 `->` 使用，表示该步骤有副作用：

```
-> @<操作>
-> @<操作>  !<错误类型>
-> @<操作>  !<错误类型>{-><处理动作>}
```

**规则**：
- `@` 是副作用标注，标明该步骤涉及 IO/事件/外部调用
- 命名空间建议在文档开头列出，以便快速了解有哪些渠道的副作用

### 5.8 循环迭代

```
loop <变量|对象>:
    -> <处理>
    -> <处理>
```

**规则**：
- 变量/对象不必是真实变量，而是一种遍历或循环的意图表达
- 循环体内可使用所有流程符号（`->`、`?=`、`@` 等）

### 5.9 闭包/回调

不在伪代码中进行闭包定义，使用自然语义说明这是个闭包，逻辑在函数外独立编写。

使用 `&fn <函数名>` 表示函数引用：

```
fn CreateOrder:
    >>:
        ...
    -> ...
    -> 定义闭包 逻辑参考 `&fn checker`
    -> 通过闭包(&fn checker)检查订单有效性
    -> ...

fn checker:
    -> ...
```

**规则**：
- `&fn <名>` 表示引用另一个独立定义的函数作为闭包/回调
- 被引用的函数逻辑在当前函数外独立编写
- 步骤描述优先使用功能性语言（如"通过闭包检查有效性"），而非详细实现代码

### 5.10 嵌套规则

- 错误处理 `{}` **不可嵌套**
- 其他嵌套不能超过 **3 层**
- 超过 3 层的逻辑需要提取子函数或定义闭包

### 5.11 完整示例

```
fn create_order:
    >>:
        user_id: UserId
        items:   Vec<Item>
    <<:
        Result<OrderId>

    // 前置: 必要信息加载
    -> 获取用户  !UserNotFound  !DbError
    -> 检查用户可下单  !UserOrderBlock{->返回失败}

    // 处理: 业务处理流程
    -> 获取信息
        ||-> 获取当前价格
        ||-> 获取当前库存信息
        ||== 合并  !PriceError  !StockError
    -> 计算风控检查结果
        ?=通过{-> Ok()}
        ?=不通过{-> return Err()}

    -> 创建订单

    // 后置: 信息保存或推送
    -> @DB::订单保存  !DbError{->回滚}
    -> @Kafka::"publish@topics"  // 引号内的 @ 不需要转义，不会引起 "" 提前结束
```

## 六、结构体

```
struct <结构体名>:
    <字段名>: <类型>           // 可附行尾注释
    <字段名>                  // 可省略类型
    ...
    impl <外观名>
```

**规则**：
- 省略生命周期标注
- 一般省略可见性标注
- 必须附注释说明用途
- 语义相关类型不可省略（如 Option、Arc），纯实现细节可省略
- `impl` 说明结构体实现了某接口外观
- 超过 10 行建议分片

**示例**：

```
struct AppState:
    pool                             // 数据库连接池
    nats: NatsClient                 // NATS 消息客户端
    config: AppConfig                // 应用配置
    secrets: Arc<SecretStore>        // 密钥存储
    permission_cache: Arc<PermissionCache> // 权限缓存
    admin_role_id: Option<Uuid>            // 管理员角色ID，可为空
```

## 七、枚举

```
enum <枚举名>:
    <变体名>
    <变体名>(<类型>)
    <变体名>(<类型>, <类型>)
```

枚举成员使用 Rust 类型语义。

**示例**：

```
enum SignalValue:
    Bool(bool)
    Numeric(f64)
```

### 结果标注

| 符号 | 含义 | 对应 Rust |
|------|------|-----------|
| `Ok(x)` | 成功返回 x（x 可不传） | `Ok()` |
| `Err(X)` | 失败，错误类型 X | `Err()` |
| `Some(x)` | 有值 | `Some()` |
| `None` | 无值 | `None` |

## 八、状态机

### 8.1 状态枚举定义

使用枚举定义所有合法状态（语法同第七章）：

```
enum <状态枚举名>:
    <状态名>
    ...
```

### 8.2 转换规则定义

**单向状态转换**：

```
states <状态枚举名>:
    <源状态> --> <目标状态>
        *-> <触发条件描述>
        *-> <另一触发条件>
```

**双向状态转换**：

```
states <状态枚举名>:
    <源状态> <--> <目标状态>
        *-> <正向触发条件>
        <-* <逆向触发条件>
```

**规则**：
- `states` 后跟与之配对的枚举名
- `-->` 声明单向可达，不可反推
- `<-->` 声明双向可达
- `*->` 缩进于所属转换下，描述正向触发条件
- `<-*` 缩进于所属 `<-->` 下，描述逆向触发条件
- 同一转换可有多个触发条件，任意一个满足即可触发

### 8.3 多目标状态

**紧缩写法**（目标状态无需分别说明触发条件时）：

```
<源状态> --> <目标A> | <目标B>
    *-> <触发条件>
```

**展开写法**（需分别说明触发条件时）：

```
<源状态> --> <目标A>
    *-> <条件A>
<源状态> --> <目标B>
    *-> <条件B>
```

### 8.4 状态机示例

```
enum 文档状态:
    Draft
    Submitted
    Reviewing
    Approved
    Rejected

states 文档状态:
    Draft <--> Submitted
        *-> 提交
        <-* 前端修改
    Submitted --> Reviewing
        *-> 指定评审人,发起评审
        *-> 定时任务自动发起评审
    Reviewing --> Approved
        *-> 评审通过
    Reviewing --> Rejected
        *-> 评审拒绝
```

## 九、接口（Traits）

用于描述接口、Facade、Traits 等，表达一个服务应该具有的外观。

**定义格式**：

```
interface <接口名>:
    fn <方法名>
    fn <方法名>
    ...
```

**实现标注**（在结构体中）：

```
struct <结构体名>:
    ...
    impl <接口名>
```

**示例**：

```
interface 脚本服务:
    fn start
    fn stop

struct Rhai脚本引擎:
    impl 脚本服务
```
