# review_checklist.md

## 目标

提供统一的 review 检查清单，确保评审输出稳定、一致、可执行。

## 使用原则

- review 必须结合对应的 PRD / Spec / Plan
- review 不仅检查代码正确性，还要检查设计一致性与复杂度控制
- review 结论必须明确区分严重程度

## 一、设计一致性检查

### 设计一致性必查项

- [ ] 是否能映射到明确的 PRD / Spec / Plan
- [ ] 是否实现了计划之外的大块能力
- [ ] 是否跳过了既定模块边界
- [ ] 是否引入了未在 spec 中说明的新状态 / 新流程 / 新依赖
- [ ] 是否存在设计偏移但未说明原因

### 常见问题

- 实现范围明显大于计划范围
- 某个模块承担了不属于其边界的职责
- 本应在 spec 中定义的行为被直接写进实现
- 多模块耦合但没有设计依据

## 二、代码质量检查

### 代码质量必查项

- [ ] 是否明显违反 SOLID
- [ ] 是否存在超长函数 / 超大类 / God Object
- [ ] 是否存在重复逻辑
- [ ] 是否存在隐式共享状态
- [ ] 是否存在命名含义不清
- [ ] 是否存在过度设计或不必要抽象
- [ ] 是否存在异常处理不一致
- [ ] 是否存在明显难以测试的结构

### 重点关注

- 单一职责是否清晰
- 依赖方向是否合理
- 抽象是否为当前问题服务
- 新增复杂度是否有明确收益

## 三、风险与验证检查

### 风险与验证必查项

- [ ] 是否说明了验证方式
- [ ] 是否有关键路径缺少验证
- [ ] 是否影响现有兼容性
- [ ] 是否存在回归风险
- [ ] 是否需要迁移 / 配置 / 数据变更说明
- [ ] 是否有潜在性能 / 并发 / 状态一致性风险

## 四、文档与可维护性检查

### 文档与可维护性必查项

- [ ] 是否补充了必要文档
- [ ] 是否补充了关键注释或说明
- [ ] 是否能让后续维护者快速理解
- [ ] 是否保留了必要的设计上下文

## 五、Review 输出格式

review 结论统一按以下结构输出：

### 必须修改

列出阻断合并或阻断交付的问题。

### 建议修改

列出不一定阻断，但强烈建议处理的问题。

### 可接受例外

列出当前可接受但存在折中的点，并说明理由。

### 总结结论

从以下结论中选择一个：

- `pass`
- `pass_with_changes`
- `request_changes`
- `blocked`

## 六、问题严重程度建议

### 阻断级

适用于：

- 与 PRD / Spec / Plan 明显不一致
- 违反关键架构边界
- 明显高风险缺陷
- 缺失关键验证
- 引入严重复杂度问题

### 重要级

适用于：

- 明显代码异味
- 命名或结构设计不清
- 设计有偏移但可修复
- 验证不充分但仍可补

### 建议级

适用于：

- 风格一致性
- 可读性改善
- 局部抽象优化
- 文档补充

## 七、Review 简版模板

```markdown
## review_result

### 必须修改
1. ...
2. ...

### 建议修改
1. ...
2. ...

### 可接受例外
1. ...

### 总结结论
request_changes
```
