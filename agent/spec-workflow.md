# spec_workflow.md

## 目标

定义组织统一的软件交付流程，确保 AI 在需求、规格、计划、实现、评审各阶段输出边界清晰、结构一致、可追踪。

## 流程优先级说明

- 本文件用于定义整体流程框架
- 在流程定义冲突时，`instruction.md` 优先级高于本文件
- 项目本地 override 可以补充流程细节，但**不能覆盖组织级禁止项**

## 总流程

标准流程如下：

```text
PRD -> Spec -> Plan -> Coding -> Review
```

如发现前一阶段信息不足或关键约束缺失，应回退到对应阶段补充，而不是直接跳过。

---

## 阶段一：PRD -> Spec

### 输入（PRD -> Spec）

- `prd<xx>.md`

### 标准输出路径（PRD -> Spec）

- `docs/prd/prd<xx>_spec/`

### 最低输出要求（Spec -> Plan）

至少包含：

- `00-overview.md`
- `01-<module>.md`
- `02-<module>.md`
- `99-open_questions.md`

文件名统一使用 `snake_case`。

### 目标（PRD -> Spec）

- 将需求拆解为可设计、可讨论、可验证的模块规格
- 明确模块边界、职责、依赖、异常与状态变化
- 形成后续计划拆分的基础

### 必须遵守（PRD -> Spec）

- 禁止生成**实际语言实现的代码**，防止过早陷入具体语言语法层面
- 业务逻辑描述优先使用：`text art > mermaid > markdown 表格 > 伪代码系统`
- 逻辑表达统一遵循 `pseudocode-system.md`
- 所有假设必须显式标记：`[ASSUMPTION:<text>]`
- 所有待确认项必须显式标记：`[NEEDS_DECISION:<topic>]`
- 所有需要决策的问题，必须列明可选方案
- 若某个决策会影响两个以上设计方向，必须在决策项中说明影响范围

### 无人值守推进规则

当存在待确认问题时：

1. AI 必须先列出决策选项
2. AI 必须基于当前上下文，自主选择**最合理、最优**方案继续推进
3. 同时在 `99-open_questions.md` 中记录：
   - 问题
   - 备选项
   - AI 当前采用的默认方案
   - 该决策可能影响的设计方向
4. 后续人工可覆盖该决策，但在人工确认前不得阻塞整体设计推进

### 完成标准（PRD -> Spec）

- 模块边界清晰
- 每个模块职责单一
- 依赖关系明确
- 存在 open questions 汇总
- 输出结构可直接进入 plan 阶段

---

## 阶段二：Spec -> Plan

### 输入（Spec -> Plan）

- `docs/prd/prd<xx>_spec/`

### 标准输出路径（Spec -> Plan）

- `docs/prd/prd<xx>_plans/`

### 最低输出要求

至少包含：

- `00-overview.md`
- `01-<module>.md`
- `02-<module>.md`

文件名统一使用 `snake_case`。

### 目标（Spec -> Plan）

- 将规格拆分为可执行、可验证、边界清晰的实现模块
- 明确每个模块的改动范围、依赖、验证方式与执行顺序
- 优先安排需要用户预先参与的步骤

### 必须遵守（Spec -> Plan）

- 禁止生成**实际语言实现的代码**
- 每个计划模块必须可独立验证
- 每个计划模块应尽量只覆盖单一职责边界
- 需要用户预操作、环境准备、权限申请的任务，必须优先排前
- 如果 spec 中仍有重大未决问题，plan 必须显式标出风险与依赖

### 完成标准（Spec -> Plan）

- 计划项之间边界清晰
- 可按模块逐步实现
- 每个模块有明确验证方式
- 可以直接进入 coding 阶段执行

---

## 阶段三：Plan -> Coding

### 输入（Plan -> Coding）

- `docs/prd/prd<xx>_plans/`
- 对应模块计划文档

### 目标（Plan -> Coding）

- 基于 plan 中已定义的模块执行实现
- 保证实现与计划、规格、需求一致

### 必须遵守（Plan -> Coding）

- 必须存在对应的 plan 模块后才能编码
- 每次编码必须映射到某一个明确的计划模块
- 不允许跨多个模块混合修改，除非显式说明原因与影响
- 如发现 plan 无法支撑实现，应先回退补 plan 或 spec

### 编码失败处理

若同一段代码连续修改 5 次仍无法通过编译或验证：

- 必须生成失败日志：`logs/failed_logs_<yyyymmdd_hhmmss>.md`
- 停止继续盲改该段代码
- 输出失败原因、已尝试方案、建议后续动作

### 完成标准（Plan -> Coding）

- 改动可映射到计划模块
- 行为与 spec 保持一致
- 验证方式已执行或已说明无法执行原因

---

## 阶段四：Coding -> Review

### 输入（Coding -> Review）

- 代码变更
- 对应 PRD / Spec / Plan

### 目标（Coding -> Review）

- 校验实现是否与设计一致
- 识别设计偏移、代码异味、复杂度与可维护性问题

### 必须检查

- 是否符合 PRD / Spec / Plan
- 是否违反 SOLID
- 是否存在明显代码异味
- 是否引入不必要复杂性
- 是否存在缺失验证或风险未说明

### 完成标准（Coding -> Review）

- review 结论清晰
- 问题按严重程度分类
- 可形成明确后续动作

---

## 回退规则

以下情况必须回退到前置阶段：

### 回退到 PRD

- 需求目标不清晰
- 非目标范围不明确
- 核心业务约束缺失

### 回退到 Spec

- 实现前发现模块边界不清
- 状态流 / 数据流未定义
- 异常处理策略缺失
- 多模块耦合无法拆解

### 回退到 Plan

- 计划拆分不可执行
- 验证方式不明确
- 实际改动范围与计划不匹配

---

## Open Questions 处理规则

- 统一收敛到 `99-open_questions.md`
- 文件名使用 `snake_case`
- 每个问题至少包含：
  - 问题描述
  - 决策选项
  - AI 当前默认采用方案
  - 影响范围
  - 是否影响两个以上设计方向

建议格式：

```markdown
## q1_<问题标题>

- 背景：...
- 决策选项：
  - A: ...
  - B: ...
- AI 当前采用：A
- 影响范围：module_a、module_b
- 是否影响两个以上设计方向：是
```
